# 读取后端验证

使用标准库的可复现控制台基准，无 BenchmarkDotNet 或其他 NuGet 依赖。从 Quire 仓库根目录运行：

```powershell
$env:DOTNET_TieredCompilation = '0'
dotnet run --project benchmarks/Quire.Package.Benchmarks.csproj -c Release -- benchmarks/results/read-backends.json
```

结果保存到指定 JSON；源文件和临时包在系统临时目录创建，完成后清理。计时包括路径解析、流/结果生命周期、实际读取、必要的解压解密；完整内容读取还包括 SHA-256 及 Meta。数值 Meta getter 微基准单独记录，不混同为资源加载吞吐。

## 枚举与读取热路径（合并索引前的历史测量）

本节保留引入合并索引前的逐包实现测量。当前公开 API 自动构建合并索引，预算不足时回退，没有用户可选的索引模式；重新运行下面的命令会测量当前自动策略，应按 JSON 中的程序集 SHA 区分版本，不能直接视为本节历史结果的复现。当前实现的逐包/合并索引内部对比见下一节。

```powershell
$env:DOTNET_TieredCompilation = '0'
dotnet run --project benchmarks/Quire.Package.Benchmarks.csproj -c Release -- --hot-paths benchmarks/results/hot-paths-after.json
```

该模式生成 2,048 个 4 KiB 文件、129 个隐式目录，以及包含 32 条 metadata-only 覆盖的第二个包。分别测量原始、LZ4、AES-GCM、LZ4+AES-GCM 数据在 RandomAccess 和 MemoryMapped 后端的三轮同步读取。随机内容使用固定种子；文件一半可压缩、一半随机。

分配量使用 `GC.GetAllocatedBytesForCurrentThread`，仅测同步调用线程；每项先预热再测量。一次枚举操作表示完成一次 `foreach`，包括创建返回路径字符串，结果不保留；查询操作包含一次 `FileExists` 和一次 `GetFileInfo`。复用读取器项在打开同一个 4 KiB 文件后反复读取其中 256 字节，包含已缓存解码块带来的收益，打开读取器的成本不在此项中。完整 `Read` 包含元数据查找和 SHA-256 校验。

结果属于热系统缓存和热库缓存，不代表冷盘带宽、异步并发性能或大文件吞吐。程序集 SHA-256、运行时、每轮耗时和分配量均写入 JSON。改造前的数据保存在 [hot-paths-before.json](results/hot-paths-before.json)，改造后的数据保存在 [hot-paths-after.json](results/hot-paths-after.json)；前者使用旧 API，不包含新增目录枚举及复用读取器项。

2026-10-28，本机 .NET 10.0.14 / Windows，Release，关闭分层编译，三轮中位数如下。前六项使用未压缩、未加密数据和 MemoryMapped 后端；AES 两项也使用 MemoryMapped。

| 操作 | 每轮次数 | 改造前耗时 | 改造后耗时 | 改造前 B/次 | 改造后 B/次 |
|---|---:|---:|---:|---:|---:|
| 枚举全部 2,048 个文件 | 20 | 26.120 ms | 7.508 ms | 633,296 | 139,360 |
| 递归枚举指定目录内 32 个文件 | 200 | 59.377 ms | 1.204 ms | 149,504 | 2,272 |
| 枚举指定目录的 16 个直接文件 | 200 | 57.151 ms | 0.601 ms | 145,664 | 1,120 |
| FileExists + GetFileInfo | 10,000 | 11.399 ms | 8.274 ms | 528 | 0 |
| ReadAt 4 KiB | 5,000 | 5.718 ms | 3.911 ms | 528 | 0 |
| Read 4 KiB，包括 Meta 和 SHA-256 | 1,000 | 4.557 ms | 4.411 ms | 648 | 64 |
| AES ReadAt 4 KiB | 5,000 | 169.816 ms | 14.972 ms | 616 | 232 |
| LZ4 + AES ReadAt 4 KiB | 5,000 | 168.629 ms | 15.179 ms | 616 | 232 |

普通 `foreach` 的枚举分配主要是结果路径字符串：本次完整枚举减少 78.0%，目录递归枚举减少 98.5%，直接文件枚举减少 99.2%。新增目录 API 每次枚举全部 129 个目录分配 6,272 B，枚举 `data` 下 64 个直接目录分配 2,656 B。复用 `AssetReader` 的 256 B 范围读取在所有四种数据组合及两种后端均测得 0 B/次；这个结论限定于已预热的读取器和块缓存。

各场景并非全部加速：未压缩、未加密的 RandomAccess `ReadAt` 5,000 次在本轮从 24.262 ms 变为 35.904 ms，同时分配从 528 B/次降到 0。此项仍包含实际操作系统读取，当前数据不足以区分系统波动与代码差异，因此不据此宣称所有后端吞吐都提升。压缩/加密的单次 `PackageSet.ReadAt` 仍创建读取器，分配为 232 B/次；需要连续随机读取时可复用 `OpenRead` 返回的 `AssetReader`。

该历史版本中，热缓存、同步单线程的 5,000 次 4 KiB `PackageSet.ReadAt`，MemoryMapped 在四种编码组合下均较快：

| 数据编码 | RandomAccess | MemoryMapped | MemoryMapped 加速比 |
|---|---:|---:|---:|
| 原始 | 35.904 ms | 3.911 ms | 9.18× |
| LZ4 | 34.210 ms | 6.222 ms | 5.50× |
| AES-GCM | 47.497 ms | 14.972 ms | 3.17× |
| LZ4 + AES-GCM | 43.780 ms | 15.179 ms | 2.88× |

复用同一读取器、反复读取同一文件内 256 B 的 10,000 次调用，RandomAccess / MemoryMapped 分别为：原始 20.550 / 0.296 ms，LZ4 0.178 / 0.179 ms，AES 0.188 / 0.180 ms，LZ4+AES 0.178 / 0.165 ms。后三种在预热后直接命中解码块缓存，几乎不再经过文件后端，因此差异很小；原始数据仍由后端读取。冷盘、真正的异步并发及大文件顺序读取没有在此次热路径基准中重测，不将上述加速比外推到这些场景。

## 合并索引与逐包索引

```powershell
$env:DOTNET_TieredCompilation = '0'
dotnet run --project benchmarks/Quire.Package.Benchmarks.csproj -c Release -- --merged-index benchmarks/results/merged-index.json
```

此基准通过友元访问内部的 `IndexMode = AssetIndexMode.PerPackage` 和 `AssetIndexMode.Merged` 做强制对照；这些不是公开配置选项。公开 API 自动构建合并索引，预算不足时回退，用户可用 `MaxMergedIndexBytes` 调整预算，并通过 `IndexInfo.IsMerged` 查看实际是否使用合并索引。两种内部策略读取同一组 8 个包：基包含 8,192 个 128 B 文件，后续 7 个补丁各包含 128 条内容覆盖和 128 条 metadata-only 覆盖，其中一半的路径在每层重复覆盖。最终可见文件数仍为 8,192，目录数为 513，不含根目录。

每种索引模式分别使用常驻目录区段（`MaxResidentIndexBytes = 64 MiB`）和分页目录区段（阈值为 0），每包页缓存保持 8 MiB，合并索引预算为 64 MiB。固定使用 MemoryMapped 读取包。查询、枚举前均预热；分页数据在缓存中，这些结果不代表缺页或冷盘性能，也不测量内容读取吞吐。常驻与分页场景反转索引模式测试顺序。

每项记录三轮耗时、进程 CPU 时间和调用线程托管分配；短批次的 CPU 时间可能因系统计时粒度记为 0。打开包先预热一次，再独立测量三次，包含校验和索引构建，不含关闭包；热路径包括命中/未命中的文件与目录查询、全量/指定目录/直接文件枚举，以及全量/直接目录枚举。每次枚举都是完整 `foreach`，包含结果路径字符串分配。

`IndexInfo.MemoryBytes` 记录合并索引保留的数组容量预算，不代表整个进程或全部索引内存；逐包策略返回的 0 不表示逐包目录、页缓存没有内存开销。原始 JSON 保留历史的模式标签格式；当前基准从 `IndexInfo.IsMerged` 生成这些标签，同时记录文件/目录计数、回退标志、打开分配量和程序集 SHA-256，并验证自动策略在零预算时回退至逐包索引。较高的打开成本、额外常驻数组与查询收益需要结合各自负载比较，不预设合并索引在所有场景都更快。

|---|---:|---:|---:|---:|---:|
| 文件查询命中 | 20,000 | 32.485 | 7.866 | 206.597 | 48.546 |
| 文件查询未命中 | 20,000 | 26.803 | 5.981 | 207.748 | 44.810 |
| 目录存在 | 20,000 | 29.486 | 4.644 | 247.199 | 29.254 |
| 目录不存在 | 20,000 | 11.021 | 4.122 | 217.333 | 31.657 |
| 全量文件枚举 | 10 | 8.712 | 2.221 | 32.820 | 21.510 |
| 指定目录递归文件枚举 | 200 | 0.663 | 0.196 | 4.608 | 1.974 |
| 指定目录直接文件枚举 | 200 | 0.640 | 0.192 | 3.732 | 1.208 |

在这个 8 包数据集中，合并索引的全部查询与枚举场景均较快：常驻模式文件查询命中快约 4.1 倍，全量文件枚举快约 3.9 倍，全量目录枚举快约 38.4 倍。四种查询在两种索引模式下均为 0 B/次；枚举的分配量相同，例如一次全量文件枚举为 557,168 B，一次全量目录枚举为 24,720 B，主要是返回的路径字符串。

## 索引表示的内存探针（实现前的设计估算）

```powershell
dotnet run --project benchmarks/Quire.Package.Benchmarks.csproj -c Release -- --index-memory benchmarks/results/index-memory.json
```

这份历史报告来自合并索引实现前的独立表示探针，其 `MergedRow` 和目录节点类型是用于比较字段布局的假设模型，不是实际 PackageSet 索引的完整内存测量。使用 100,000 项、48 字符 ASCII 路径，预分配字典，记录三轮中最小的当前线程托管分配量；它不测查询速度、存活堆、进程工作集或索引构建峰值。代码见 [IndexMemoryProbe.cs](IndexMemoryProbe.cs)，历史原始结果保留于 [index-memory.json](results/index-memory.json)。

当前实现的核心数组为每文件 28 B（24 B 文件引用加 4 B 邻接编号）、每目录 40 B，另含一个根目录节点；该成本叠加在已有包索引之上。实际运行库的预算、打开成本和性能测量见上节 [合并索引与逐包索引](#合并索引与逐包索引) 及 [merged-index.json](results/merged-index.json)。

2026-10-28，.NET 10.0.14 / x64，结果如下；数组的总分配包含 24 字节数组头，表格按项取近似值：

| 表示 | 字节/项 | 边界 |
| --- | ---:| --- |
| 假设的统一文件引用数组 | 24.00 | 两个 64 位记录号、两个 32 位包号；引用已有索引，不含路径副本 |
| 假设的目录节点数组 | 32.00 / 40.00 | 两种示例字段布局；完整设计可能需要额外字段 |
| 直接子文件的邻接编号数组 | 4.00 | 32 位编号，独立于文件记录与目录节点 |
| `Dictionary<string, int>` | 30.42 | 不含已存在的键字符串 |
| `Dictionary<string, 紧凑文件引用>` | 47.80 | 不含已存在的键字符串 |
| `Dictionary<string, 完整解析记录>` | 265.06 | 不含已存在的键字符串；值模拟运行库的内容/Meta 包引用及两条完整记录 |
| 48 字符路径字符串及单独的引用数组 | 128.00 | 字符串约 120 字节，引用数组约 8 字节/项；字典方案不必保留此额外数组 |

当前 `EntryRecord` 值类型在此运行时占 104 字节，包含两条记录及两个包引用的解析值占 224 字节。这是解码后的值类型大小；当前常驻包索引保留的是原始编码字节，仍按每条 **128 字节记录＋UTF-8 路径**计算。

本次字典容量为 108,631，实际开销受容量、装载率、运行时、路径长度和 Unicode 内容影响。若字典自行持有新路径字符串，需在字典行数据上再加字符串开销。紧凑结构数组与已有索引是叠加关系；快速查询若依赖分页路径仍可能需要 I/O。统一索引设计的内存范围与适用场景见 [README](../README.md#现有索引与统一索引的内存取舍)。

## 数据与测量边界

2026-10-26，i7-13700KF（24逻辑处理器）、Windows 10.0.28000、.NET 10.0.12，Release，关闭分层编译。

以下原始数据和程序集哈希来自更名前的版本；项目重命名后保留测量记录，复测命令使用当前 Quire.Package 项目名。

- 3000个小资源：80%为1KiB、15%为4KiB、5%为64KiB；一半随机、一半可压缩数据，各有四字段Meta。
- 一个16MiB随机数据资源，用于大资源局部和顺序读取。
- 四种配置：原始、LZ4、AES-GCM、LZ4+AES-GCM；默认块大小256KiB。
- 小资源每轮12000次随机读取；大资源每轮1500次随机4KiB读取。
- 同步1/4线程，异步1/4/8/16个worker，各3轮。后端顺序在不同配置间交替。
- 每个后端先预热内容和Meta；**结果属于热系统缓存，不是冷盘带宽**。没有清空操作系统缓存，没有修改系统电源计划。
- 映射后端的 ReadAsync 可以同步完成，异步worker可能顺序执行；不能将其“8个worker”解读为8个CPU线程。同步4线程场景使用 Parallel.For，原始数据也保存在JSON中。

## 结果与选择

以下为12000次随机范围读取（最多4KiB）的三轮耗时中位数，单位ms：

| 配置 | RandomAccess 同步1 | 映射 同步1 | RandomAccess 异步8 | 映射 异步8调用 |
|---|---:|---:|---:|---:|
| 原始 | 90.86 | 11.11 | 49.37 | 10.65 |
| LZ4 | 42.87 | 16.22 | 23.22 | 17.40 |
| AES-GCM | 228.67 | 179.70 | 64.38 | 181.26 |
| LZ4 + AES-GCM | 206.60 | 178.87 | 61.92 | 179.89 |

映射在本机热缓存的未加密小读中有明显收益；加密资源的异步并发读取使用 RandomAccess 更快。默认保留 RandomAccess，提供 `ReadOptions.ReadMode = AssetReadMode.MemoryMapped` 显式选择，不根据这组热缓存结果自动启用映射。

1500次大资源内随机4KiB读取，同步单线程中位数：

| 配置 | RandomAccess | 映射 |
|---|---:|---:|
| 原始 | 9.54 ms | 1.96 ms |
| LZ4 | 26.74 ms | 15.14 ms |
| AES-GCM | 81.80 ms | 68.87 ms |
| LZ4 + AES-GCM | 82.45 ms | 68.19 ms |

压缩或加密时，4KiB范围仍可能需要处理完整256KiB块，不能将返回的字节数解释为底层处理字节数。

两百万次数值/布尔 Meta getter 调用耗时34.9–37.1ms，测得额外托管分配0字节。测量对象是已加载的Meta，排除了首次解析、字符串解码和磁盘I/O。

原始数据包含全部轮次、P95/P99、CPU、分配量、工作集及程序集摘要：[read-backends.json](results/read-backends.json)。测量程序集 SHA-256：`AC6D331B70EC0AB3657A54AAF90BF27C88C7B718E900F978E346B04C68267ED6`。工作集包含测试程序和运行时；同进程首次打开时间包含初始化因素，不作为冷启动结论。

冷盘、多盘型和生产资源集的收益仍需在目标环境测量。对于映射模式，还需考虑页错误在调用线程上发生，异步接口不能消除该等待。
